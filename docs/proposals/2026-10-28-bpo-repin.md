## 1. The situation

The repository vendors one BPO file, `ontology/apqc-ext.ttl`. It is pinned in
`config/upstream-sources.yaml` at:

- commit `66131945b525c54f44e4962f32bb1f52dfa0cd12`;
- SHA-256 `1b9a9375…cab4b`;
- namespace `http://example.org/apqc#`, prefix `ex`.

From that file the extract `vendor/bpo/bpo-ext-bco-extract.ttl` carries six act genera: Acquisition,
Development, Improvement, Organizational Establishment, Remuneration and Reporting. For
each it keeps the class, label, definition, comment and superclass.

BPO has since moved:

- **v0.4.0** (`327ea2c`) moved every BPO IRI to `https://fandaws.com/ontology/bpo#`, with
  local names unchanged. BPO's notice names `327ea2c` as the re-pin target.
- **v0.4.1** (`dda9fa5`, notified at `bc64e91`) renamed BPO's prefix label from `ex:` to
  `bpo:`, with no IRI change.

The old pin is still reachable and its bytes are unchanged, so nothing is broken today.
BCO, however, still cites IRIs that BPO has abandoned. They sit under `example.org`, a
domain reserved for documentation that nobody will ever serve.

The inventory already harvests BPO at `bc64e91` (I-1). The vendored extract is a separate
pin and has not moved.

## 3. Options

**A. Re-pin to `327ea2c`, the target BPO named, and keep the label `ex:`.**

- In the extract, only the IRI base and `owl:versionInfo` change.
- CM-01's bytes and statements stay true.
- The repository would then hold two BPO commits: the extract at `327ea2c` and the
  inventory at `bc64e91`.

**B. Re-pin to `bc64e91`, the inventory's commit, and keep the label `ex:` (recommended).**

- Everything in A happens. In addition, three vendored comments change wording (`ex:` to `bpo:`
  inside BPO's own prose).
- One BPO commit across the repository, so the inventory and the extract cannot drift
  apart.
- CM-01's bytes and statements stay true.

**C. Re-pin to `bc64e91` and adopt `bpo:` as the label everywhere.**

- Matches BPO's own Turtle.
- Requires a new, reviewed CM-01 version (six tokens and the line-94 wording), the
  checker's prefix list, and the tests.
- It cuts across the specification, which uses `ex:` for BCO terms as well. Doing this
  before spec v0.5 resolves that doubled use would leave the draft spec and the
  repository disagreeing.

**D. Do not re-pin now.**

- Nothing breaks.
- BCO goes on citing IRIs that BPO has abandoned and that no one will serve.
- The gap grows with every BPO release.

## 4. Recommendation

**Option B, followed by the label rename as part of spec v0.5 and CM-01's next reviewed
version.**

- B brings BCO's IRIs up to date with one BPO commit across the repository.
- It leaves approved CM-01 untouched, because CM-01 names the genera through `ex:` without
  stating an IRI.
- The rename to `bpo:` belongs with v0.5, which must in any case stop using `ex:` for BCO's
  own terms (RP-5). Doing both together changes CM-01 once, in a reviewed version.

## 5. What the re-pin PR would contain (under B)

1. `config/upstream-sources.yaml`:
   - BPO commit `bc64e91839378e1926189c01bf184d6a22d5c1b7`;
   - the new URL and digest (`a8119728…c6fd`);
   - namespace `https://fandaws.com/ontology/bpo#`;
   - the licence URLs at the new commit (same digest);
   - prefix still `ex`.
2. Regenerate the extract, `config/upstream-extracts.json` and `vendor/NOTICE.md` with
   `vendor_upstream.py --rebuild`. Show in the PR that the new extract equals the old one
   with the base rewritten, apart from `owl:versionInfo` and the three comments.
3. Update `tests/test_namespace.py` for the new namespace, keeping the overlap guard and
   its falsification test.
4. Change the inventory's baseline cross-check. The baseline stays `66131945`, recorded as
   "the commit the vendored extract pinned when I-1 was reviewed". I-1's outputs stay
   byte-identical, and the PR shows their digests unchanged against your I-1 approval
   record.
5. Update `CLAUDE.md`, `HANDOFF.md` and `DEVELOPMENT.md` where they describe the pin, and
   rebuild the site.
6. Draft an acknowledgment to BPO in `communications/bpo/outgoing/`, saying the re-pin is
   done (BPO's notice invited one). Sending it is your call.
7. Record in the decision record that CM-01's `ex:` tokens now expand to BPO's new IRIs for
   the same terms, so the change is visible rather than silent.
