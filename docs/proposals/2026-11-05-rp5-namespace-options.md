## 1. What is to be decided

The specification's register reads: "A permanent namespace before release. Provisionally
`https://fandaws.com/ontology/bco#` (ADR-003 D1)." ADR-003 adds that "`#` versus `/` for
every namespace above" is RP-5's. The two differ in scope: the register names one
namespace, and ADR-003 names five (closure matrix §2, item 3). **This note treats RP-5 as
covering all five**, because ADR-003 requires that a change of form changes "every row of
this table in one commit". So the decision has three parts:

1. **Authority:** the domain, or a persistent-identifier service.
2. **Form:** `#` or `/`.
3. **Scope:** one namespace, or all five together.

## 2. Where things stand

| Namespace | Provisional IRI | Holds |
|---|---|---|
| `bco:` | `https://fandaws.com/ontology/bco#` | Ontology terms. None is minted yet, apart from the vocabulary's annotation properties and the `bco:PCFCode` datatype |
| `bcom:` | `https://fandaws.com/ontology/bco-metamodel#` | 9 metamodel concepts, Draft |
| `bcoc:` | `https://fandaws.com/ontology/bco-catalog#` | 5 catalog concepts, Draft |
| `bcos:` | `https://fandaws.com/ontology/bco-sources#` | Source records, generated from the register |
| `bcoa:` | `https://fandaws.com/ontology/bco-agents#` | Declared agents |

- **Nothing resolves.** The public site says "BCO IRIs identify terms but do not resolve
  over HTTP".
- **There is a sixth, unlisted IRI space.** The vendored extracts are named under
  `https://fandaws.com/ontology/bco/vendor/` (`EXTRACT_BASE`), a slash path below `bco`.
  These are ontology IRIs, not terms, so no shape filters them today.
- **The upstreams, as vendored:**
  - **BPO** (sibling project, same domain): `https://fandaws.com/ontology/bpo#`, hash.
  - **CCO:** `https://www.commoncoreontologies.org/` + `ont…`, slash-style opaque
    identifiers.
  - **BFO:** `http://purl.obolibrary.org/obo/` + `BFO_…`, slash-style under a PURL
    service.
- **Nothing ratified binds a BCO IRI.** No vocabulary concept is ratified. The signed G1-T
  records and the decision records name `bco:BusinessCapability` as a CURIE, not as a full
  IRI. A namespace change therefore breaks no act. Records stay as written and read through
  the prefix.

## 3. The options

| | A. Keep the domain, hash | B. Keep the domain, slash | C. A persistent-identifier service |
|---|---|---|---|
| IRIs | `https://fandaws.com/ontology/bco#Term`, as today | `https://fandaws.com/ontology/bco/Term` | e.g. `https://w3id.org/<name>/…`, redirecting to wherever the files are served |
| Change now | **None** to IRIs. Remove "provisional" from the list, the specification, ADR-003 and the site. Move `EXTRACT_BASE` out from under `bco` only if the architect wants it out | One commit across about 23 tracked files: tools, shapes and their fixtures, tests, schema, generated vocabulary (rebuilt), site text. The test in `tests/test_namespace.py` enforces it | The same one commit as B, with the form chosen. Plus a registration with the service, which is an outward act and the architect's |
| Resolution | One document per namespace: the fragment is resolved by the client | Per term: the server must answer every term IRI, or redirect it | The service redirects; the server behind it can change |
| Depends on | Long-term control of `fandaws.com` | The same, plus per-term serving | The service's continuity, not the domain's |
| Fits | BPO (same domain, hash) | CCO and BFO (slash) | BFO's PURL practice |
| Risk | The domain lapsing breaks every IRI | The same; and if `bco/` became a namespace, the vendored extracts' IRIs (`bco/vendor/…`) would fall inside it, so `EXTRACT_BASE` must move | A slower first step, and every IRI depends on an external service |

**What every option shares**: one commit for all five namespaces (ADR-003 D1); the
`AUTHORED_NAMESPACES` list and every shape filter changed together; the vocabulary
regenerated by `tools/vocab/build.py`, never edited; and the release check of spec §10
("The permanent namespace is decided (RP-5)") met by the decision record.

## 4. What the team cannot settle

- Whether the architect controls `fandaws.com` for the long term, and intends to serve the
  ontology there. A and B rest on that.
- Whether BPO will move with the BCO. Its namespace is BPO's own; a change there is a message
  to that team, not a change here.

## 5. Recommendation

**A, for all five namespaces**, if the architect will hold `fandaws.com` and serve one
document per namespace there:
- it changes no IRI;
- it matches BPO, the project the BCO takes its act types from;
- and hash IRIs need no per-term server.

**C** is the choice if the domain's future is uncertain. It costs the one commit now, while
nothing is minted or ratified. That cost grows with every term minted later.

In either case, a sub-choice: move `EXTRACT_BASE` to a path outside `bco` (for example
`https://fandaws.com/ontology/bco-vendor/`), so that no extract is ever named inside an
authored namespace.

## 6. Boundary

This note adds no candidate, act, object property or OWL. It changes no namespace, list,
shape or record. It makes no G1-I claim and declares no part of CP-0 complete.
