## 1. Recommendations

**(a) LinkML as the schema and validation layer for authored YAML: GO-LIMITED.**

Limited to this: one LinkML schema describing the shape of an authored concept
record, `gen-json-schema` as the only generator used, and `linkml validate` (or
plain JSON Schema validation of the generated schema) as a CI check over the
authored YAML. Inside that scope it did what it claimed: the generated JSON Schema
was byte-identical across every run, path and hash seed measured on this machine
(CRLF on Windows; see section 4 for what that means on Linux), every sample
term was accepted, and all 21 negative fixtures were rejected with a message that
names the slot at fault.

Outside that scope it is a no-go, for reasons measured below:

- it cannot carry the rules that matter most in ADR-003 — derived status (D5), the
  digest binding of a ratification (D2), "a Ratified definition does not change in
  place" (D3), the §4 extraction (D4), the quote tripwire and claim status (D6),
  "the agent is declared" (D8). Those are Python in P3 whatever is chosen here;
- the RDF it makes of data (`linkml-convert`) has blank nodes for every inlined
  object (8 in the valid sample), which D9 forbids, and it has no way to mint the
  content-derived IRIs D9 asks for. The vocabulary graph must come from the
  repository's own serializer, not from LinkML;
- one of its constraint forms is wrong in a way that passes silently
  (`value_presence: ABSENT` on more than one slot of a class, section 5.2);
- the environment is 91 packages and 176 MiB, against 15 packages and 44 MiB for
  the whole of the normal suite, and an unpinned install pulled 20 packages less
  than two weeks old (section 2).

Whether the go-limited scope is worth that environment is the architect's call. A
hand-written JSON Schema, or plain Python checks, would cover the same 21 fixtures
with no new dependency; LinkML's advantage over them is that the schema is also
readable documentation of the record, and that it is the same file a later
`gen-pydantic` or `gen-doc` could read. Nothing measured here needs it.

**(b) `gen-shacl` versus hand-written SHACL: NO-GO for `gen-shacl`. Hand-written
shapes stay.**

- Its output is **not reproducible**: six runs, six different digests. With the
  default random hash seed the graphs are not even isomorphic —
  `sh:ignoredProperties` is an RDF list built in set-iteration order; a fixed
  `PYTHONHASHSEED` fixes the graph but not the bytes (section 4).
- On ADR-003's model it produces shapes **pyshacl 0.40.1 refuses to load**
  (`ClosedConstraintComponent must have at most one sh:closed predicate`): both
  concept kinds are `skos:Concept`, `gen-shacl` keys a shape by class URI, and the
  two kinds and their abstract base merge into one `skos:Concept` shape carrying
  `sh:closed false, true`.
- With the merge removed (a variant with distinct class URIs, never committed), the
  shapes load but **reject both valid samples** — patterns written for the CURIE
  form (`^bcoa:…`) are applied to the expanded IRI — and of the 10 defects that
  could be expressed in RDF at all, it **catches 3 for certain and misses 5**:
  neither conditional rule (`rules:` are not translated; 3 fixtures), and neither
  pattern declared on a type without a `uri` (`GitCommit`, `Sha256Hex`). The other
  2 trip patterns that fire identically on valid data.
- It writes **no `sh:message`** (0 of 56 property shapes), **no SPARQL target**,
  and 82 blank nodes. `tools/ontology/validate.py` identifies an inline constraint
  by the digest of its message; with no messages, every generated constraint would
  share one identifier, and `tests/test_ontology_checks.py` could not list them by
  name. The repository's ladder cannot be run on it as written.

`gen-owl` was measured too, though not asked about: no-go (section 6).

## 2. The environment

**Pinned release: `linkml==1.11.1`** (uploaded 2026-05-20), with `linkml-runtime==1.11.1`
(the same day). The two-week rule against 2026-10-23 admits anything uploaded before
2026-10-09.

- `linkml 1.12.0` (2026-10-08) was eligible by one day, but was uploaded six hours
  after its last release candidate and followed by 1.12.1 five days later. 1.11.1 has
  been out five months.
- `pip install linkml==1.11.1` alone, with the repository's `rdflib==7.6.0`,
  `pyshacl==0.40.1` and `PyYAML==6.0.3`, resolved **88 packages, 20 of them uploaded
  less than two weeks before** the trial. Among them was `linkml-runtime 1.12.1`
  (2026-10-13), a newer minor than the `linkml` it serves. Pinning the top-level
  package reproduces whatever was newest that day.
- `trials/p2-linkml/requirements-linkml-trial.txt` therefore pins **the whole
  installed set: 91 packages**. Each of the 20 young packages is held at its newest
  final release before 2026-10-09. Holding `linkml-runtime` at 1.11.1 changed the
  graph: it brought in `pystow`, `tqdm` and `backports.zstd`, which are pinned too.
- **Verified the one way it can be:** installed into an empty venv, then `pip freeze`
  compared with the file: 91 pinned, 91 installed, none unpinned, none missing, no version mismatch. `pip check`: no broken requirements.
- **No conflict with the repository's pins.** The resolver accepted `rdflib==7.6.0`,
  `pyshacl==0.40.1` and `PyYAML==6.0.3` unchanged. One pressure to note:
  `linkml-runtime` 1.12.x requires `rdflib>=7.6.0`, so the repository's pin is
  already the floor of the next runtime.
- **Size:** `site-packages` 175.9 MiB (184,494,786 bytes) (venv 186.4 MiB), against 43.7 MiB for the
  normal `.venv` (15 packages). A clean install from the pinned file took 1 min 59 s with a warm pip cache (the first, cold install of the unpinned set ran past a 10-minute tool timeout)
  on this machine.
- **What comes with it:** Sphinx (a hard dependency of `linkml`), `sphinx-click`
  and six `sphinxcontrib` packages, SQLAlchemy, openpyxl, pyoxigraph, PyShEx,
  Jinja2, pydantic, and `pytest` itself (`prefixcommons` requires
  `pytest-logging 2015.11.4`, which requires `pytest`). None of these is used by the three generators
  measured; all of them become part of what CI must install and keep pinned.

`requirements-dev.txt` is unchanged. Nothing in the normal suite installs or imports
the trial environment.

**Line endings.** On Windows the generators write text-mode stdout, so every output
captured here is CRLF (`gen-json-schema` 534 CR bytes; `gen-shacl` 340 CR bytes; `gen-owl` 687 CR bytes). The repository's digests are over LF bytes, and CI

the build normalises line endings or LinkML writes the file itself. The LF-normalised
digests are given in the table so a Linux run can be compared; **no Linux run was
made**. Separately, `gen-owl --help` crashed under the Windows console encoding
(`UnicodeEncodeError: 'charmap' codec can't encode character '→'`), so any
non-ASCII text in a schema is a further cross-platform hazard unless
`PYTHONIOENCODING=utf-8` is set.

  Reading the results instead: of the 10 fixtures `linkml-convert` could express in
  RDF, it reports the named defect in 3 (`notation-not-pcf-code`,
  `ratification-path-outside-decisions`, `source-id-malformed`); in 2 the defect is
  a pattern that fires on valid data too (`metamodel-in-catalog-scheme`,
  `drafted-by-not-an-agent-iri`); and it misses 5: both `departs-from` fixtures and
  `deprecated-without-replacement` (conditional rules), `ratification-short-commit`
  and `ratification-empty-file-digest` (type-level patterns).
- **11 of the 21 defects cannot be written as RDF by LinkML's own converter** even
  with `--no-validate`: the Python data classes refuse unknown enum codes, missing
  required slots, unexpected properties and bad datetimes before any RDF is made. So
  "does the generated SHACL catch it" is unanswerable for them through LinkML.

### 5.2 Rule by rule

| ADR-003 rule | Expressed? | How, or why not |
| --- | --- | --- |
| Base concept: prefLabel, definition, inScheme, sources, drafted-by, created, ratified_by, wasRevisionOf, isReplacedBy | **yes**, with one gap | slots with `slot_uri`s; `created` as `datetime`; `ratified_by` inlined |
| prefLabel **with a language** | **partly** | LinkML 1.11.1 has no language-tagged literal type. A label is an object `{value, language}`, which in RDF is a blank node with two properties, not an `rdf:langString`. The wellformedness shapes' drift rule compares `LANG()` of literals, and would see none |
| MetamodelConcept: `designatesClass` required | **yes** | `slot_usage: required` |
| CapabilityCatalogConcept: `designatesClass` optional | **yes** | |
| Catalog: broader only, never narrower | **yes, by omission** | `narrower` is not a slot of the class; classes are closed (`additionalProperties: false`), so an authored `narrower` is "Additional properties are not allowed" |
| `notation` typed as a PCF code | **yes** for the lexical form | a `PCFCode` type with `uri: bco:PCFCode` and a five-digit pattern. The five-digit form is the trial's assumption, to be checked against PCF 7.4 before P3 relies on it |
| SourceReference: SRC id `^SRC-[A-Z]+-[0-9]{2}$`, locator, relation enum, departure_note | **yes** | slot pattern; `SourceRelation` enum |
| `departs-from` requires a `departure_note` (and a locator) | **yes in JSON Schema; no in SHACL** | a class `rules:` block (precondition `relation equals_string departs-from`, postconditions `required`). `gen-json-schema` writes `if/then`; `gen-shacl` drops it |
| `departs-from` must cite a claim at V or P | **no** | a lookup into `register.yaml`; LinkML has no cross-document constraint |
| RatificationReference: path, 40-hex commit, SHA-256, record digest | **yes** | patterns; the empty-file digest refused by a negative lookahead in the `Sha256Hex` pattern (JSON Schema and Python both accept the lookahead; `gen-shacl` drops the whole type pattern) |
| D2: the digest is the SHA-256 of `git show <commit>:<path>`, commit reachable from `main` | **no** | needs git |
| `lifecycleStatus` never authored | **yes, by omission** | not a slot of any authored class |
| `owl:deprecated` never authored | **yes, by omission** | as above |
| A metamodel concept carries no `definition` (D4) | **yes, by omission** | `definition` is a slot of the catalog class only |
| `value_presence: ABSENT`, the obvious spelling of the four rules above | **unreliable** | enforced when one slot per class is ABSENT (probes 1–3 rejected), **silently not enforced** when two or more are: `gen-json-schema` folds them into one `not: {required: [a, b, c]}`, which refuses only a record that authors all of them at once (probe 4 accepted). The trial schema's first draft used it, and four fixtures that should have failed passed |
| Authors write only Draft or Candidate | **yes** | `AuthoredStatus` enum |
| Deprecated requires a replacement | **yes in JSON Schema; no in SHACL** | `rules:` on the build-output class `BuiltConceptStatus` |
| … and then `owl:deprecated` is `true` | **no** | an `equals_string: "true"` on a boolean slot becomes a JSON Schema `const` of the *string* `"true"`, which rejects the boolean `true` (probe `probe_conditions.yaml` (a): `'true' was expected`). 1.11.1 has no boolean value condition |
| Status is derived (D5): Deprecated, then Ratified, then authored | **no** | a computation over the act files and git; out of any schema language's reach |
| A Ratified concept's definition does not change in place (D3) | **no** | history |
| Provenance nodes get IRIs minted from their content (D9) | **no** | `SourceReference` and `RatificationReference` have no identifier, so they are blank nodes in RDF; LinkML has no content-addressed identifier |
| `drafted_by` names a **declared** agent (D8) | **form only** | a `^bcoa:` pattern; that the IRI exists in the agents graph is cross-document |
| Single-value `inScheme` per kind | **yes in JSON Schema, wrong in SHACL** | `equals_string` is refused on a `uriorcurie` range by `gen-shacl` ("require range 'string'"; probe `probe_conditions.yaml` (b)), so the value is a pattern, which SHACL then applies to the expanded IRI |

| --- | --- | --- |
| node shapes | 6 (8) | 2 |
| property shapes | 56 (56) | 3 |

| sh message | 0 (0) | 5 |
| sparql targets | 0 (0) | 2 |

| severity declared | 0 (0) | 5 |
| closed | 7 (8) | 0 |

The repository's hand-written pattern, which `gen-shacl` does not reach:

- **SPARQL targets by namespace** (`STRSTARTS(STR(?this), "https://fandaws.com/ontology/bco#")`),
  because the data graph holds vendored terms that must not be judged. `gen-shacl`
  targets by `sh:targetClass` only, so a shape applies to whatever is typed with the
  LinkML class — the BCO's concepts are typed `skos:Concept`, which is exactly where
  the merge in section 1(b) comes from.
- **A message on every constraint**, written for the person who will read the
  report. `gen-shacl` writes none.
- **Language-aware drift rules in SPARQL**, which need `LANG()` on literals that
  LinkML does not produce.
- **The ladder** (`tools/ontology/validate.py`): every shape set runs against the
  corpus and against a negative fixture, counts are pinned in the baseline, and
  messages are listed by name in `tests/test_ontology_checks.py`. Generated shapes
  would arrive with no messages to list, blank-node constraints whose only stable
  identity in `validate.py` is their message digest, and bytes that change every
  build, so the baseline could not be recorded.

**`gen-owl`: no-go.** Its bytes differ on every run (the graphs are isomorphic, so
this is blank-node ordering: 229 blank nodes). With default options it mints
schema-local properties (`bcotrial:broader`) rather than using the `slot_uri`s. With
`--no-use-native-uris` it writes axioms about other vocabularies' terms: 14 subjects in SKOS, PROV, DC Terms and OWL get triples, among them `dcterms:created` (range dateTime; type DatatypeProperty), `dcterms:isReplacedBy` (range anyURI; type DatatypeProperty), `dcterms:source` (range SourceReference; type ObjectProperty), `owl:deprecated` (range boolean; type DatatypeProperty), `skos:Concept` (exactMatch CapabilityCatalogConcept), `skos:broader` (range anyURI; type DatatypeProperty).
That is redeclaring upstream terms, which this repository never does. The BCO's TBox
is hand-authored in `ontology/`; nothing here needs an OWL rendering of the record
schema.

## 7. What was not done

- **No Linux run.** CI is Linux. The determinism table is from one Windows machine;
  the LF-normalised digests are there so a Linux run can be compared, and that
  comparison is the first thing to do if (a) goes ahead.
- **No second machine**, and no clean clone at a different depth: the path test
  copied `trials/p2-linkml/` only, which is all the generators read.
- **No `gen-pydantic`, `gen-python` or `gen-doc`.** Not asked, and not needed for the
  go-limited scope.
- **The schema is a trial, not the record.** It has not been reviewed against P3's
  YAML layout, and the PCF lexical form is assumed.
- **`jsonschema` validation without LinkML** (validating the authored YAML against the
  committed generated JSON Schema with the `jsonschema` package alone) was not
  measured separately; `linkml validate` uses it underneath, so the results above
  should carry over, but that is an inference.
- **The young-package rule was applied to the transitive set by hand**, from PyPI
  upload dates on 2026-10-23. Nothing enforces it.
