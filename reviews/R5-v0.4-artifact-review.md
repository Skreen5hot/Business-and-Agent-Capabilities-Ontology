# R5 Review — BCO Specification v0.4 versus v0.1 Artifacts and BPO

**Date:** 2026-10-22  
**Disposition:** Retain architecture; revise before ADR-002 ratification / executable migration.  
**Scope:** User-supplied `Business Capability Ontology v0.4.md`, v0.1 ZIP package, BFO 2020 and CCO 2.0 PDF source serializations, and selected public BPO `main` files inspected 2026-10-22. Public `main` remains mutable; pin before release.  
**Not performed:** Full integrated OWL-DL reasoning or complete CAP-01–31 SHACL / SPARQL test suite.  

## Executive decision

The v0.4 specification is stronger than the v0.1 artifact and is the proper proposed target. It now distinguishes ontological type admission (G1-T), actual bearer attribution (G1-I), and operational adequacy. No v0.4 Turtle implementation has been supplied. The existing v0.1 ZIP implements seven classes and basic examples/shapes only. Migration is a code change plus new evidence/validation infrastructure, not a file rename.

### Key confirmed source facts

1. **BFO material basis:** `BFO_0000218` (`has material basis`) relates a disposition to a material entity that is a continuant part of its bearer at a relevant time.
2. **CCO organization:** `cco:ont00001180` is a Group of Agents; `cco:ont00000300` restricts **has member part** (`BFO_0000115`) to Agent, not indiscriminately every possible `has continuant part` assertion. Distinguish a modeling policy from a formal entailment.
3. **CCO Plan:** `cco:ont00000974` is a Prescriptive ICE and directly has `BFO_0000178 some cco:ont00000476` (Objective). The pattern is verified; OI-19 can close on the supplied release, although CAP-31 still needs explicit named target validation.
4. **CCO integer value:** `cco:ont00001773` (`has integer value`) has domain `cco:ont00000253` **Information Bearing Entity** (an Object), not an Information Content Entity. Do **not** apply it to `cco:ont00001010` ordinal measurement ICE: the domain inference is ontologically incompatible with GDC-vs-object typing. This is a hard blocker for CAP-20's literal profile.
5. **Current BPO:** Public `ontology/slices/apqc_1_0.ttl` contains `ex:BusinessModelGovernanceCapability rdfs:subClassOf [ owl:onProperty obo:BFO_0000054 ; owl:someValuesFrom ex:P20955 ]` (approximately lines 2015–2020). OI-9's claim that the current slice has no such restriction is incorrect for the inspected public `main`.
6. **Current BPO:** The same slice defines `ex:BusinessAuthorization` under CCO Action Permission (approximately lines 515–520); OI-16 is a confirmed migration conflict.
7. **Current BPO:** `capabilities/capability_scope.json` still says it generates `enablesProcess` and derived `requiresCapability`. The disable/removal decision has not yet been demonstrated by generator output.
8. **v0.1 package:** `tests/check_draft.py` completed (exit 0) and reported 5 parsed Turtle files with 15 + 44 + 14 + 17 + 22 triples; 7 classes, 0 new object properties, no existential realization restrictions *in v0.1 modules*. That does not cover the existing BPO existential restriction.

## Findings (recommended review R5 dispositions)

| ID | Severity | Sections / artifacts | Finding | Recommended action / falsifying fixture |
|---|---|---|---|---|
| R5-01 | BLOCKER | CD2, CAP-25, G1-I | “A group of agents contains no artifact parts” is **stronger than the formal CCO `has member part` restrictions**. `has material basis` requires physical continuant parthood, not merely organizational ownership or a membership label. Moreover CAP-25 rejects artifacts but does not require any positive material-basis triple. | Explicitly call the member-agent-only basis a **BCO house modeling policy**, not a formal CCO entailment. Require each asserted basis target to be a **named material agent** and an actual `BFO_0000115` member part of the bearer; keep time and parthood caveats. Define how absence of recorded grounding affects G1-I. Negative fixture: basis agent not a member; positive fixture: member-and-basis assertions. |
| R5-02 | BLOCKER | CAP-20, OI-8, instance pattern 1 | The candidate CCO numeric property `cco:ont00001773` is defined on an **Information Bearing Entity**, not an ordinal measurement ICE. The spec leaves the rating's value unresolved, so CAP-20 cannot be implemented as specified. | Choose a value encoding consistent with CCO **before** CAP-20 is marked executable. Do not put `ont00001773` directly on the rating ICE. A carrier/ICE separation or an approved existing annotation/other property must be validated against the pinned closure. Include a fixture that tries the wrong integer property directly on the rating and must fail. |
| R5-03 | HIGH | OI-9, CD8, BPO slice 1.0 | The current source **does include** an existential realization on `BusinessModelGovernanceCapability`, contrary to v0.4 OI-9's uncertainty. | Mark OI-9 **confirmed** for inspected `main`; remove/refactor `BFO_0000054 some ex:P20955` as a BPO change. Verify other copies across all slices before closure. |
| R5-04 | HIGH | CAP-26, class/example `CapabilityAssessment` | Class definition says assessment “describes an organization,” while the sample and CAP-26 require `describes` of a **capability instance**; these targets differ. An assessment can refer to the organization, the capability instance, and a type IRI; their roles are not interchangeable. | State a canonical pattern: assessment `is about` organization (or explicitly `describes` if warranted), `describes` known capability instance when present, and `concernsType` the class. For absent findings, no instance link. Add fixtures for swapped/missing targets. |
| R5-05 | HIGH | CAP-21, G1-I, CQ-3 | Valid act class membership is not enough to establish organizational exercise: an unrelated vendor process could be asserted to realize the consumer's disposition and still pass CAP-21. | Reuse `BFO_0000057` `has participant` (or vetted CCO agent participation property) to validate a participation/performance witness appropriate to the bearer and act. Require evidence of the organization's own performance; do not invent an object property. |
| R5-06 | HIGH | CAP-26, CQ-1, G1-I | CAP-26 checks asserted `has capability` triples, not all individually asserted Business Capability instances or inverse `capability of` / BFO `bearer of` statements. The named inverse can bypass the evidence gate. | Make a canonical ABox profile: all asserted K1 capability individuals must have one explicit organization bearer and one present-finding G1-I assessment. Validate both property directions (or normalize once then validate). |
| R5-07 | HIGH | CD15, CAP-18, CQ-5 | Validity dates and completeness are specified, but the **applicability algorithm** is underspecified: exact act type versus subclasses; principal organization versus personnel; overlapping permissions, multiple authorities, revoked/superseded records; closed-world scope. | Add an explicit CQ-5 query semantics table and positive/negative fixtures for each dimension, with unknown outside scope. Prospective authorization records remain ICEs, not asserted Action Permissions. |
| R5-08 | HIGH | RP-2, CAP-03, CD12 | `ex:enablesProcess` is a legacy/generated **annotation**, not a modal OWL relation. Reusing it as realization index is valid as a software convention, but its causal-sounding label must not become an ontology claim; property kind and generation are still OI-6. | Require an `owl:AnnotationProperty` declaration check, scoped generation output test, and clear documentation “admissible realization index, not actual enablement.” Do not remove the old generator until consumption audit. |
| R5-09 | MEDIUM | CD2 / Known limits | “Losing an artifact makes a capability unavailable; it does not make it cease” is categorical. Whether it changes grounding depends on the bearer and the exact dispositions involved. | Say **may remain latent** under the narrow member-grounded profile; platform-loss cases require G1-T/G1-I re-evaluation, possibly OI-14. Fixture: platform loss with unchanged members versus loss of embodied member capacity. |
| R5-10 | MEDIUM | CD6, CAP-09 | The supplied BFO function definition distinguishes biological evolution and **artifacts designed** for a function. The fact that an organization is purposefully designed does not by itself prove Function for its dispositions. | Tighten Function review criteria to BFO's origins, not a generalized “organization was designed” argument. Preserve no-disjointness. |
| R5-11 | MEDIUM | CD14, CAP-17/27, CQ-6 | `partial` refers to criteria but no evidence of a declared type/scale/scope is required beyond `dct:conformsTo`; missing `present` is corrected, but semantic distinction between incomplete component coverage and incomplete dispositional existence remains. | Define `partial` as “partial coverage of a declared assessment criterion,” never partial being. Include mixed-source fixtures and specify a reportable criterion identifier. |
| R5-12 | MEDIUM | CD16, CAP-29, CQ-12 | “No downstream triple **generated** from CQ-12” is a pipeline property, not something ordinary SHACL over the final graph can establish from assertions alone. | Move CAP-29 to generator/provenance tests (not just Gate C), retaining an assertion-level rule against unsubstantiated integration findings. |
| R5-13 | MEDIUM | CD17, CAP-31, OI-19 | The supplied CCO Agent Ontology **already** states Plan ⊑ `has continuant part some Objective`, confirming the proposed target-state superclass/pattern. However existential OWL satisfaction does not ensure a named target linked in asserted data. | Close OI-19 for the pinned-equivalent supplied release; keep CAP-31 as a named-object SHACL check. |
| R5-14 | MEDIUM | K1 and generic definition, CAP-03 | The parent `ex:BusinessCapability` is exempt from the realization index, but its proposed definition says every capability is indexed to types “in its realization index.” | Word the parent definition in terms of realizability of types of planned acts; specify index as a requirement for named **specific subclasses**. |
| R5-15 | LOW | RP-9, TM-1 | Dropping `BusinessCapabilityDescription` is defensible while the type catalog remains authoritative, but loses portability of independent versioned capability dictionary descriptions. | Keep OI-17 open; do not reintroduce a redundant ICE absent a concrete use case. |
| R5-16 | LOW | migration, coverage, manifests | v0.4 introduces files not in the v0.1 package (`apqc-cap.ttl`, `apqc-cap-desc.ttl`, scope/coverage evidence schema files, migration manifest); none has been shown as executable. | Treat as implementation backlog, not as passing CAP requirements. |

## Disposition on ratification items

- **RP-1:** revise; separate formally entailed restrictions from the house's stricter member-agent basis policy, add actual part-of evidence and noncategorical artifact-loss handling.
- **RP-2:** accept in principle; verify index annotation kind, code generation and performance evidence.
- **RP-3:** accept as design decision, but repository implementation is outstanding.
- **RP-4:** accept conditionally on downstream manifest consumer audit.
- **RP-5:** accept, permanent namespace remains blocking for release.
- **RP-6:** revise assessment targeting semantics and evidence representation.
- **RP-7:** revise CQ-5 authorization applicability/completeness and evidence graph semantics.
- **RP-8:** accept model of component possession only; move pipeline-only validation to appropriate gate.
- **RP-9:** approve vocabulary with a blocker on the maturity value property.
- **RP-10:** accept type/instance split, strengthen the G1-I ABox profile and grounding checks.

## Recommended implementation order

1. Resolve R5-01 (member-part grounding policy) and R5-02 (ordinal rating data property).
2. Fix BPO existential legacy axiom and document BPO `BusinessAuthorization` retrofit.
3. Define a canonical assessment and bearer ABox pattern, then test G1-I and CAP-26.
4. Declare and validate capability index generation and class-register manifests, then implement CAP-03/21.
5. Define authorization applicability, completeness manifest schema and query fixtures.
6. Migrate the seven v0.1 classes via a rename manifest; preserve no equivalence commitments.
7. Run complete BFO/CCO/BPO closure reasoning and SHACL with both positive and falsifying fixtures; capture commit and dependency content hashes.
